移动端「软键盘露白」攻坚复盘

Next Terminal · 2026-09-12 · 案例档案：一个「修了 5 轮未根治」的真机 bug 如何通过调试数据闭环

一句话结论

该 bug 消耗约二十轮对话的根本原因不是技术难度，而是在无法本地复现的环境里靠猜测改代码——5 轮修复中 3 轮方向错误、其中 1 轮是反向的。建立「真机 → 开发机」的实时遥测通道后，2 轮闭环。这个对比本身就是结论。

一、问题与背景

现象：iPhone 访问堡垒机 PWA，SSH 终端页呼出软键盘时出现白色留白；普通 shell 漏、TUI（Claude Code 类）不漏；后用户又报告双指缩放同样触发、且页面可上下滑动。

环境特殊性：iOS 软键盘的行为（视觉视口平移、动画中间态、`dvh` 不收缩）无法在桌面浏览器与 Playwright 中复现；生产为纯 HTTP（iOS 不注册 Service Worker，但 SW 在桌面环境又存在更新滞后）。

二、完整时间线

轮次依据假设与改动结果
v1.4.35无数据猜「WebGL 画布未重绘」→ fit 后加 term.refresh()；同时把 init 的 fit 收敛到统一入口无效 且埋下 fit 未执行的新 bug（见第四节）
v1.4.36无数据补 visualViewport.scroll 监听 + overscroll-behavior半对 scroll 监听是必要的，但未触及真因
v1.4.37无数据猜「fixed 退化成跟随滚动」→ 加 window.scrollY 补偿反向 位移被算两遍，露白从偶发变必然
v1.4.38用户三张真机截图（带诊断浮层数值）定位 scrollY ≡ offsetTop（同一位移的两种表达）→ 去掉 scrollY稳态修复 但动画过程仍有问题
v1.4.39截图（稳态无白底）禁双指缩放、offsetLeft 补偿；据单张截图误判「已闭环」误判 用户报「还是会出现」
v1.4.41~42—建立遥测通道：手机 → 生产同源转发 → 开发机接收器；诊断浮层实时上报视口事件时序通道打通（经历：手机跨域 fetch 被拦 → 改同源转发）
v1.4.43107 条 vv-event 时序定位真因：120ms 防抖被动画期 ~17ms 间隔的连续事件流永久重置，容器在弹出动画全程（~700ms）不更新；动画结束还残留 19px 错位。→ 容器对齐改 rAF 每帧执行，与重排解耦白底消除
v1.4.44用户反馈「快速小范围抖动」rAF 相位差 → 改同步写；高度渐变 → 40px 阈值冻结可用状态（用户确认，残留轻微）

三、真因（数据还原）

键盘弹出动画期间，iOS 以 ~17ms 间隔连续触发 scroll/resize 事件约 700ms，innerHeight 从 812 连续收缩到 469、visualViewport.offsetTop 从 0 连续爬升到 343。原视口同步采用 120ms 防抖——

连续事件流 → 防抖计时器每次被重置 → applySize 全程不执行
→ 容器停留在键盘弹出前的位置（整个动画期间露白）
→ 动画结束后防抖终于触发，但读到的是触发时刻的旧值（残留 19px 错位）

修复原则：「对齐」与「重排」解耦——容器样式（top/height/left）每帧/同步跟随视口（轻量、无重排副作用）；body 高度锁定与 xterm fit（重操作）保留防抖，动画结束后一次执行。

四、过程中揪出的另一个潜伏 bug

v1.4.35 埋下的「fit 从未执行」：init 里把 fitAddon.fit() 收敛为统一入口 fit()，而 fit() 读的是 state fitAddon——init 中 setFitAddon 尚未执行，fit() 拿到 undefined 直接 return；随后的尺寸同步 effect 又因「尺寸值不再变化」不触发。结果 xterm 一直停留在默认 80×24（画布 720×432）被 CSS 拉伸到整个容器——影响所有终端的渲染质量，因无人检查渲染内容而潜伏 8 个版本。

教训：回归测试只验证「结构」不验证「渲染内容」，等于没有渲染回归。

五、方法论沉淀（为什么反复失败）

  1. 无数据时的猜测成本极高：5 轮猜测 3 轮错、1 轮反向（把「有时露白」变成「必然露白」）。真机数据一到，一轮定位。
  2. 单点截图 ≠ 时序数据：截图只能看到稳态；问题发生在动画过程。遥测的事件时序（vv-event / vv-apply）才是证据链。
  3. 版本验证是前提：SW 更新滞后导致用户可能测的是旧版。诊断浮层的「构建标记」一行字省掉了一整轮无效验证。
  4. 测试判定方式的陷阱：xterm WebGL 渲染器没有 DOM 文本节点，用 textContent 判定渲染结果会得到假阴性（本次排查中一度被误导，误以为「渲染坏了」）。渲染判定要用像素采样。
  5. 「先取证、后动代码」应成为不可复现环境的铁律：诊断通道应该在第一轮就建，而不是第五轮。

六、调试设施方案档案（本次已停用，供后续深度沟通）

架构

手机页面→生产 /api/telemetry
（同源 + 登录态）→开发机接收器 :9090
（Go，JSONL 落盘）

手机无法直连开发机（跨域 fetch 被手机网络拦截；浏览器导航却可通）——同源转发是必须的。接收器必须带请求日志（否则无法区分「手机没发」与「发了没到」）。

采集内容（两级）

级别内容开关
错误类window.error / unhandledrejection / console.error（含白屏前最后一刻的错误、断开瞬间现场）始终开启
事件类每次视口事件的即时数值（vv-event）、防抖后写入容器的值与 rect（vv-apply）诊断浮层开启时

安全边界

  • 仅内网开发机可达；上报内容只有错误信息与视口数值，无任何业务数据（密码/资产/会话内容不采集）
  • 批量 500ms 合并、队列上限、失败退避、keepalive 保证重载前最后一批发出
  • 转发端点挂全局 Auth（需登录态）

能力边界

  • 能分析：前端 JS 侧一切「真机有、本地无」的现象——视口/键盘/缩放/滚动时序、白屏前错误、接口异常、机型差异、操作时序还原
  • 不能分析：业务/后端问题（会话内容、协议错误、审计数据）、JS 进程彻底死亡后的行为

七、后续深度沟通议题（建议清单）

  1. 产品化定位：临时排查工具 vs 常驻诊断能力？开关由谁控制（用户/管理员/版本开关）？
  2. 数据生命周期：采集内容分级、留存时长、脱敏规则（审计产品对遥测数据的合规要求）
  3. 正式端点设计：复用现有基础设施还是独立通道？性能与安全边界（批量、限流、鉴权）
  4. 诊断入口形态：隐藏式（如长按 logo）vs 显式按钮 vs 异常时自动出现
  5. 与审计定位的契合：遥测是否可演进为「会话质量数据」（延迟、断线率、渲染健康度）
