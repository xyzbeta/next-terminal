## v1.4.44 更新内容（终端视口：消除键盘/滑动后的「小范围快速抖动」）

> 承接 v1.4.43（露白真因已修）。用户复测确认**白底基本处理**，但呼出键盘或手指上下滑动后画面会快速小范围抖动一小会。复测数据（vv-apply 5/5 全对齐）证明稳态正确，抖动来自动画过程的两处相位问题：

| 类别 | 内容 | 说明 |
|------|------|------|
| 修复 | **容器对齐改同步执行（去 rAF）** | scroll 事件天然每帧最多一次（17ms ≈ 60fps），rAF 反而引入 **1 帧相位差** —— 容器位置每帧落后视口 2~8px，快速变化时就是「小范围快速抖动」。写 top/left 不触发布局（只 paint），事件到达同步写入无 jank |
| 修复 | **高度「渐变冻结」** | 键盘开合动画期间 `innerHeight`/`vv.height` 连续渐变，每帧写容器高度会让 xterm 画布**每帧拉伸-回弹**（抖动的另一来源）。现只允许 >40px 的跳变（键盘开合瞬间，需立即响应以免输入行被遮/留白）即时生效；渐变值冻结在最近一次稳定高度，动画结束后由防抖的 `applySize` 一步到位（含 fit 与远端 resize） |

**已验证**：本地构建/lint/回归全绿。
**待真机复测**：呼出键盘 / 手指滑动，抖动应消失或显著减弱；白底应保持不回归。

## v1.4.43 更新内容（软键盘露白：真机遥测数据定位真因并修复）

> 这是「真机遥测通道」的第一份产出。此前软键盘露白修了 4 轮未根治，因为没有动画过程的数据；v1.4.42 的遥测链路打通后，用户一次测试拿到的 107 条 `vv-event` 时序直接定位真因。

### 真因（遥测数据还原）

键盘弹出动画期间（约 700ms），iOS 以 **~17ms 间隔连续触发 scroll/resize 事件**，且 `window.innerHeight` 从 812 连续收缩到 469、`vv.offsetTop` 从 0 连续爬升到 343。而视口同步用的是 **120ms 防抖**：

| 阶段 | 视口实际值 | 容器实际位置（vv-apply 实测） |
|------|-----------|------------------------------|
| 弹出动画**期间**（~700ms） | 连续变化 | **纹丝不动** —— 连续事件流把防抖永远重置，`applySize` 全程不执行 |
| 弹出结束 | vvTop=343 | top=324，**残留 19px 错位**（防抖触发时读的是旧值） |

容器在整个动画期间停留在键盘弹出前的位置 —— 这就是每次呼出键盘必见白底的原因。

### 修复：容器样式对齐与重排解耦

| 类别 | 内容 |
|------|------|
| 修复 | 拆出 `alignContainer()`：只写容器的 height/top/left 三个 inline 值（**每帧 rAF，最多一次**）。轻量无副作用，跟得上 17ms 的视口变化 —— 动画期间容器始终贴合可视区，白底不再出现 |
| 保留 | 防抖 120ms 的 `applySize` 只负责重操作：body/html 高度锁定 + `setBox`（触发 xterm fit 与远端 resize）。动画期间不执行、动画结束后执行一次，避免高频 fit 把终端来回压扁 |
| 保留 | 全部既有公式与监听（vv.offsetTop 单项、resize+scroll 双监听、scrollY 禁令），遥测打点同步保留 |

**已验证**：本地构建/lint/回归全绿（按键条、诊断浮层、断开落点、视口剧变模拟）。
**待真机复测**：呼出键盘 → 数据里 `vv-apply` 应随动画高频出现（不再只有稳态 2 条），且全程 rect 与视口吻合。

## v1.4.39 更新内容（终端视口：禁止双指缩放 + 诊断浮层加构建标记）

> 软键盘露白在 v1.4.38 已定位真因（`scrollY` 与 `offsetTop` 被重复计算）。本轮处理用户新发现的**同一根源的另一条路径**：双指缩放。

### 双指缩放会以完全相同的方式露白

用户实测：**移动端浏览器（非 PWA）不呼出键盘，只用双指放大 SSH 命令行界面，同样出现白底**。

与软键盘是同一根源 —— 两者都改变 `visualViewport`：

| 触发 | 改变的 visualViewport 属性 |
|------|--------------------------|
| 软键盘弹出 | `height` 收缩、`offsetTop` 偏移 |
| 双指缩放 | **`scale`**、`width`/`height`（= 视口/scale）、`offsetLeft`/`offsetTop` |

终端容器按 CSS 像素布局、用 `visualViewport` 数值定位；一旦 `scale` 变化，容器几何与可视区就对不上，露出页面背景。

**根因是 `index.html` 的 `user-scalable=no` 被浏览器忽略了** —— iOS Safari 自 iOS 10 起、Android Chrome 也会忽略该声明，所以缩放实际一直生效。

| 类别 | 内容 | 说明 |
|------|------|------|
| 修复 | **终端页禁止双指缩放** | 挂载期间给 `body` 设 `touch-action: pan-x pan-y`（允许平移，只关掉缩放），卸载时还原。这与 `index.html` 的原始意图一致 —— 终端需要固定行列布局，整体缩放会让布局计算出错；放大的正确路径是页面已有的**字号调节**（会让 xterm 重排，内容不错位）。已验证不影响终端的触摸滑动与抽屉内滚动 |
| 修复 | 容器定位补上 `offsetLeft` | 原先只补偿了垂直偏移。横向同理（缩放或页面被横向滚动时），容器宽度是 `100vw`，左边缘对齐到 `offsetLeft` 即可覆盖满 |
| 新增 | **诊断浮层显示构建标记** | Service Worker 对静态资源有更新滞后，用户报「还是不行」时跑的往往仍是上一版 —— 本项目已因此白跑过一轮真机验证。现在浮层首行显示 `v1.4.39-viewport` 这类标记，截图即可确认版本。**后续改终端视口相关代码请一并更新该字符串** |

**已验证**：`body` 的 `touch-action` 在终端页为 `pan-x pan-y`、离开后还原为 `auto`；TUI 触摸滑动仍正常（`less` 位置指示器由 1% 滚到 2%）；桌面端与全站 23 个路由回归全绿。

**⚠️ 仍需真机确认**：v1.4.38 的 `scrollY` 修复是否真的解决了软键盘露白 —— 本轮截图请留意诊断浮层首行的**构建标记**，若非 `v1.4.39-viewport` 则说明跑的还是旧版本（SW 尚未更新）。

## v1.4.38 更新内容（软键盘露白底：真因定位并修复）

> 上一轮我在没有真机数据的情况下加了 `window.scrollY` 补偿，**方向是错的**，反而把位移算了两遍、让露白变成必然。本轮靠真机诊断浮层的读数定位到真因。

### 真因：`window.scrollY` 与 `visualViewport.offsetTop` 在 iOS 上是同一个位移

用户提供的三张真机截图（终端页 + 诊断浮层）给出了决定性数据：

| 截图 | `vv.offsetTop` | `window.scrollY` | 容器 `inline top` | 容器 `rect top` | 结果 |
|------|---------------|------------------|------------------|----------------|------|
| 0986 | 0 | 0 | 0 | 0 | 恰好正确（两者都为 0，掩盖了错误） |
| 0987 | 127 | 127 | **254 = 127×2** | 127 | 顶部露白 127px |
| 0988 | **43** | **43** | **86 = 43×2** | **43** | 顶部露白 43px |

`容器 inline top ≡ 2 × offsetTop`，而 `rect.top ≡ inline.top − offsetTop` —— 说明 `position: fixed` 的定位基准**没有退化**，正确公式就是 `top = vv.offsetTop`。上一轮的 `window.scrollY + vv.offsetTop` 把同一个位移算了两遍，容器被推下去整整一个 `offsetTop`，露出的正是页面背景。

像素测量印证：0987 在 CSS `134→188` 处存在一条 `rgb(255,255,255)` 白带。

### 这同时解释了「为什么普通 shell 漏、TUI 不漏」

差异**不在 shell/TUI，而在页面是否被滚动过**：

- **普通 shell**：用户直接点终端输入 → 触发聚焦滚动 → `offsetTop > 0` → 错位露白
- **TUI**：多用按键条操作、不触发聚焦滚动 → `offsetTop = 0` → 恰好正确

同一套布局代码，因操作方式不同而表现不同 —— 与用户观察到的现象完全吻合。

### 附带确认的两件事（真机读数）

| 项 | 读数 | 结论 |
|------|------|------|
| `100dvh` 探针 | **812**（键盘弹出时 `innerHeight` 也是 812） | **iOS 这个 PWA 里 `dvh` 不随键盘收缩**，容器高度必须由 JS 用 `vv.height` 覆盖 —— 现有实现正确 |
| `body.clientHeight` | 344（= `vv.height`） | 高度锁定生效；容器 `rect` 与 `visualViewport` 吻合，**布局层没有问题**，此前的「渲染层」假设可以排除 |

| 类别 | 内容 |
|------|------|
| 修复 | 容器 `top` 恢复为 `vv.offsetTop`，并在代码里用三张真机的具体数字写明「为什么不能加 scrollY」，避免再次误加 |
| 保留 | 上一轮新增的 `visualViewport` **`scroll` 监听**继续保留 —— 它保证 `offsetTop` 变化时能及时重算（`resize` 与 `scroll` 是两件事，缺一不可） |
| 保留 | 诊断浮层（悬浮菜单里的 🐛）暂不移除，便于真机复验；确认无误后可随时删掉 |

**已验证**：模拟真机读数（`offsetTop=77` 且 `scrollY=77`）时容器 `top=77px` —— 位移只算一次；旧公式会给出 154px。

## v1.4.36 更新内容（「退出后重新登录」白屏真因 + 软键盘露白底）

> v1.4.35 对「PWA 白屏」的判断只对了一半：它修好的是**冷启动时 chunk 请求被挂起**那条路径（真实存在，可复现），但用户实际遇到的是**另一条**。本轮给出真因。

### 修复：退出登录后重新登录，永久停在「正在努力加载中」（真因）

用户补充的关键线索是「**只要在 PWA 里退出账号再重新登录，必现**」——不是冷启动。据此精确复现，问题出在 `Redirect` 组件的跳转时机：

```jsx
useQuery('infoQuery', accountApi.getUserInfo, { onSuccess: data => { ... navigate(...) } })   // 旧写法
```

**`onSuccess` 只在 queryFn 真正执行时触发一次**。而全局 `staleTime` 是 5 分钟，期间再次挂载 `useQuery` 会直接返回缓存、**不执行 queryFn、也就不会触发 `onSuccess`**。

完整链路：
1. 首次登录 → 缓存为空 → queryFn 执行 → `onSuccess` → 跳转 ✓
2. 退出登录 → 回到 `/login`（`react-query` 的内存缓存**没有销毁**）
3. 重新登录 → `navigate('/')` → 落回 `Redirect` → `useQuery` 命中 5 分钟内的缓存 → **`onSuccess` 不触发 → 不跳转**
4. 于是停在根路由 `/`，那里渲染的正是 `<Landing/>`（「正在努力加载中」），页面上没有任何可点的东西

杀掉应用重开（清空内存缓存）就恢复 —— 与用户描述完全一致。实测复现：修复前 `登录后 URL = /#/`，修复后 `= /#/online-session`。

| 类别 | 内容 | 说明 |
|------|------|------|
| 修复 | **跳转改由数据驱动，不再依赖 `onSuccess`** | 改为 `useEffect` 依赖 `infoQuery.data`：缓存命中时 data 立即有值，effect 照常执行。这从根上消除了「事件式跳转 + 缓存命中 = 永不跳转」的脆弱组合 |
| 修复 | **登录成功时清空 react-query 缓存**（安全问题） | 缓存里留着上一个账号的用户信息、资产、会话数据，换个账号登录会先读到旧数据（staleTime 内不重新请求）—— 既是显示错误，也是**跨账号数据泄露**。必须在「进入登录页」的所有路径上清，故放在登录成功处而非退出处（会话过期被 401 踢回、双因素中断等路径不会走「退出」） |
| 重构 | `queryClient` 抽为 `service/query-client.js` | 原先定义在 `index.js` 的模块作用域内，**没有任何模块能拿到它**，这也是缓存无法被清理的原因 |

### 修复：终端页软键盘弹出时上下露白底、且页面可上下滑动

`applySize()` 里**已经**处理了 `visualViewport.offsetTop`（注释记着「实测 offsetTop 由 0 变为 177」），但只监听了 `visualViewport.resize`：

```js
window.visualViewport.addEventListener('resize', syncSize);   // 旧：只有 resize
```

软键盘弹出时浏览器做的是**两件不同的事**：① 缩小可视区高度（触发 `resize`）；② 把可视区在布局视口内**向上平移**让聚焦的输入框可见（`offsetTop` 由 0 变正，触发的是 **`scroll`**）。而 `position: fixed` 是相对布局视口定位的。

只监听 `resize` 会拿到「新高度 + 旧 offsetTop」的组合：resize 先到、offsetTop 尚未更新，容器按过时的 top 定位 → 可视区上下两侧落在容器之外，露出页面背景（白底），页面此时又有可滚动余地，于是能上下滑动。

修复：补上 `visualViewport` 的 `scroll` 监听，并在终端页挂载期间加 `overscroll-behavior-y: none`（iOS 在 `overflow: hidden` 下仍会橡皮筋回弹把整页拖出白边；`overscroll-behavior` 才是关掉回弹的那一项）。

**已验证**：篡改容器样式后**只派发 `scroll` 事件**（不派发 resize），容器位置被正确纠正回 `top=0px height=844px`；对照实验（不派发任何事件）确认不会误触发、不存在自反馈环；`body`/`html` 的 `scrollHeight == clientHeight`，页面确实不可滚动；离开终端页后样式全部还原，不影响其它页面。
**⚠️ 未验证**：iOS 真实软键盘无法在 Playwright 中模拟，需真机确认。

## v1.4.35 更新内容（PWA 冷启动白屏修复 + 终端键盘与渲染细节）

### 修复：PWA 从桌面图标冷启动后「登录即白屏，退出重进才好」

用户反馈：加到主屏后从图标打开，登录页正常，**点登录后永久停在「正在努力加载中」**；上滑退出再点图标就能进。

**复现与定位**：该界面是路由级 `Suspense` 的 fallback —— 说明路由 chunk 的请求**既不成功也不失败**。实测拦截 `*.chunk.js` 使其不响应后，页面在「正在努力加载中」卡住 23 秒以上，控制台无任何报错 —— React.lazy 的 promise 永远 pending。

根因是 Service Worker 的**网络优先**策略：

```js
event.respondWith(fetch(request).catch(() => caches.match(...)))   // 旧实现
```

`fetch` 在 PWA 冷启动（SW 刚被唤醒、网络栈未就绪）时若**挂起**，`respondWith` 就不会 settle，页面的请求永远等下去。

| 类别 | 内容 | 说明 |
|------|------|------|
| 修复 | **SW 改为「缓存优先 + 后台更新」** | 构建产物的文件名都带 content hash，内容变了文件名就变了 —— 所以「命中缓存直接返回」永远不会拿到过期内容。冷启动因此不再依赖网络就绪。实测：第二次访问时把全部静态资源请求挂起，SW **一个网络请求都没发**（拦截数 0），页面正常渲染 |
| 修复 | **SW 网络请求加 10 秒超时** | 缓存未命中时（发版后的新 chunk）若网络挂起，中止并回退，不再把「挂起」传导给页面。超时后 chunk 加载变为**失败**，由 ErrorBoundary 接住并给出「重新加载页面」按钮 —— 比永久白屏好得多 |
| 修复 | **SW 缓存加容量上限（150 条）** | 产物名带 hash，发版即产生新条目、旧条目再不会被请求。不设上限会随发版次数无限增长（本项目曾一天迭代十余个版本）。超出后按插入顺序删最旧 |
| 新增 | **路由级 Suspense 的 fallback 带「挂起自愈」** | 新增 `RouteFallback`：15 秒仍未渲染出内容即自动整页重载一次（webpack 的 chunk 加载器会缓存失败/挂起的请求，单纯重试同一个 import 无效，必须重载让 runtime 重新初始化）；若重载后仍卡住则改为显示按钮，**30 秒冷却窗口**保证不会陷入刷新循环。这是**没有 SW 的环境**（纯 HTTP 部署，浏览器不启用 SW）下的唯一兜底 |
| 修复 | 断开连接改用 SPA 导航 | `disconnectAndBack` 原用 `window.location.href = '/#/online-session'`，在 PWA standalone 下可能被当作真实导航而触发整页重载 —— 重载又要走一遍「冷启动 → chunk 加载」，正好踩中上面那条挂起路径（表现为：标题栏已切到在线会话，内容区白屏，必须再刷一次）。改为 `navigate()`，只换组件不重载文档 |

**缓存安全边界已验证**：11 条缓存条目全是带 hash 的构建产物；`index.html` / `/` / `manifest.json` / `sw.js` **均未被缓存**（前者由服务端 `no-cache`，后三者不在 SW 的缓存扩展名白名单内）—— 发版后 `index.html` 始终取最新，其引用的新 chunk 缓存 miss 后走网络，不会出现「新入口 + 旧资源」。

### 修复：终端 WebGL 渲染器在软键盘弹出时「露白底」

上一轮重新引入 WebGL 后用户反馈：滑动有改善，但**点出软键盘仍会露白底**。

原因：WebGL 渲染器有独立的画布层与字形图集，容器尺寸变化时它按新尺寸重建画布，但**已经绘制过的区域不会自动重画** —— 容器被拉高的那部分就留下未绘制区域。

修复：新增统一的 `fit()` 包装，**所有重排路径**（初始化、字号调整、窗口尺寸变化、IME 合成结束后的延迟重排）都收敛到它，内部在 `fitAddon.fit()` 之后补一次 `term.refresh(0, rows-1)` 强制整屏重绘。走 GPU 的成本极低，且只在尺寸变化时触发。同时修正了初始化时的顺序问题：改为**先登记 `termRef` 再 fit**（`fit()` 内部要读它），否则首次重排会漏掉重绘。

**已验证**：容器高度 844→420→844→380→844 连续剧变后终端完整重排，无白色区域。
**⚠️ 未完全验证**：iOS 软键盘弹出走的是 `visualViewport.resize`（不是 `window.resize`），Playwright 无法真实模拟软键盘。两条路径最终都汇聚到同一个 `fit()`，因此修复应同时覆盖，但**需真机确认**。

## v1.4.34 更新内容（会话恢复修复 + 终端 WebGL 渲染器回归 + 移动端细节）

### 修复：会话「继续」后终端永久空白（严重）

用户反馈「会话点击继续，页面显示空白，显示不了字符」。实测复现后定位到**两个独立缺陷，缺一不可**：

### 修复：终端 WebGL 渲染器 —— 上一轮的移除是误判

v1.4.20 以「终端与容器错位、露出白底」为由移除了 `xterm-addon-webgl`。**真因是版本不匹配**：当时装的是 `xterm-addon-webgl@0.16.0`，其 peer 依赖为 `xterm ^5.0.0`，而本项目用 `xterm 4.19.0` —— addon 调用了 5.x 才有的内部渲染 API，渲染自然错乱。现改用配套的 `0.12.0`（peer: `xterm ^4.0.0`）。

为什么值得重新引入：手机 DPR 普遍 2~3，canvas 渲染器的实际画布是 780×1700 ~ 1170×2500 像素；而备用屏幕下的滚动本质是「把滚轮发给远端 → 远端整屏重绘 → 传回来重画」，一屏约 2000 个字形。**按帧合并只优化了「发送」，没优化「绘制」**。

配套防护：`onContextLoss` 时主动 `dispose()`，xterm 自动回落 canvas 渲染器（GPU 进程崩溃时降级为「卡但可用」而非白屏）；设备/浏览器不支持 WebGL 时构造抛错被 catch，同样回落。

**已验证**：WebGL 上下文正常建立；软键盘弹起/收起（容器高度 844→420→844）后终端正常重排、无露白底无错位（这正是上一轮回滚的触发场景）。

**⚠️ 未验证**：性能收益无法在本环境量化 —— headless Chromium 走 SwiftShader 软件 GL（启动参数含 `--enable-unsafe-swiftshader`），软件模拟的 WebGL 比 canvas 2D 更慢，测出的数字对真机没有参考价值。**需真机确认**。

| 修复 | **清理任务在 10 万行以上必然失败** | `DeleteByIdIn` 把无 LIMIT 扫描出的全部 ID 展开成 SQL 占位符，而 SQLite 的 `SQLITE_MAX_VARIABLE_NUMBER` 为 32766——**实测 4 万行即报 `too many SQL variables`，一行都删不掉**，清理任务只留告警刷屏，日志表只增不减，统计查询持续恶化。登录日志与计划日志改为一条区间 DELETE（实测 4 万行 85ms 删净）；会话表因需同时删录屏文件，改为分批 500 条循环 |
| 修复 | 录屏删除与数据库删除的顺序反了 | 原实现先 `RemoveAll` 录屏再删 DB 行，DELETE 失败时会出现「录屏已删、记录还在列表里」的不一致（用户看到一条永远点不开回放的会话）。改为先删行再删文件，最坏只留下无人引用的文件 |
| 修复 | `authorised` 三个分页接口的计数查询错位 | counter 用 `Table("assets")` 却按 `users.nickname` / `user_groups.name` 过滤——**实测报 `no such column: users.nickname`，带搜索参数即 500**；`FindAssetPage` 的 counter 多带 `GROUP BY assets.id`，数的是资产数而列表返回的是授权记录数（实测 2 资产 4 授权时 counter=2、列表 4 行），导致第 2 页起永远取不到数据。三处 counter 均改为与列表查询同源 |
| 优化 | 会话状态标记由「全量查 ID + 分批 UPDATE」改为一条 UPDATE | `ReviewedAll` 此前要把数万行读进内存再发出数百条 SQL |
| 修复 | `CloseSessionById` 用全局互斥锁包住了网络写与 DB 事务 | 管理员批量断开 N 个会话时全部串行排队，任一慢写（10s WriteDeadline）卡住整体。临界区收窄为「摘取会话 + 从管理器移除」 |
| 优化 | 系统负载采集移出写锁 | 原实现锁内含 `cpu.Percent(time.Second)` 固定 1 秒阻塞采样 + 4 次 IOCounters + disk.Usage，临界区约 1.1 秒而采集每 5 秒一次——读侧（前端 5s 轮询）约 21% 的请求撞锁。改为锁外采样、微秒级提交 |
| 修复 | 6 处裸读 `SftpClient` 绕过并发保护 | 直接读字段会绕过懒初始化锁，可能拿到未初始化的 nil。统一改走 `GetSftpClient()` |
| 优化 | `FindTags` / `FindByStatus` / `FindAllUnReviewed` 只取所需列 | 原实现整行读回，包含 password / private_key / passphrase 等加密大列——为拼一个标签列表载入全部资产私钥，数千资产时是数十 MB 无谓开销 |
| 优化 | 批量删除资产包一个事务 | 原实现 N 个资产 = N 个事务 × 3 条语句 |
| 优化 | 登录策略的时段查询消除 N+1 | 每次登录都会走该路径，改为一次 IN 查回后按策略分组 |
| 优化 | 存储日志补保留期清理 | 此前永不过期，与其余三张日志表的策略不一致，是库中增长最快的表。新增「存储日志保留时长」设置项 |
| 修复 | 网关照隧道端口分配的 TOCTOU | 原实现先在 localhost 探测空闲端口、再拿去绑 hostname（两个不同地址且中间有时间窗），改为直接以 `:0` 监听并回读实际端口 |

### 性能（第三轮：数据路径与前端产物）

| 类别 | 内容 | 说明 |
|------|------|------|
| 修复 | **SSH 慢观察者会卡死主会话终端** | 主输出泵此前**同步**扇出给所有观察者，每个观察者的写带 10s deadline。一个「慢而未死」的监控端（后台挂起、网络拥塞）会让 `flush` 阻塞最长 10 秒，进而经 `dataChan` 填满 → 停止读 SSH stdout → 远端 PTY 窗口填满，用户侧表现为「终端卡住」。已有的「观察者死亡摘除」只解决了写失败的场景。现改为每个观察者一条带缓冲队列 + 独立写 goroutine，主泵只做非阻塞投递、队列满即丢帧。**实测：观察者完全不消费时，2000 次扇出耗时 27ms**（修复前其中一次会卡满 10s） |
| 优化 | 消除 RDP 帧的两处全量拷贝 | `guacd.Read` 对每帧都做一次 `string(data)` 仅为与两个 22 字节常量比较（1080p 单帧可达 MB、30fps ≈ 每秒数十 MB 纯 memcpy）；handler 层再做一次 `string(instruction)`。前者改为先比长度，后者新增 `Session.WriteBytes` 直接消费 `[]byte` |
| 修复 | guacd 握手阶段无读超时 | guacd 接受 TCP 却不回数据时 `NewTunnel` 永久阻塞，而此时隧道尚未注册到任何 Session，无任何路径能解除阻塞。**deadline 只覆盖握手阶段并在返回前清除**——运行中的主循环绝不能有读超时（画面静止时 guacd 可长时间静默，超时会被误判为断线）。同时补上 `expect("ready")` 失败分支漏掉的 `conn.Close()` |
| 修复 | SSH 握手无超时 | `net.Dialer.Timeout` 只覆盖 TCP 建连，覆盖不到 version 交换与 KEX。风险链：资产巡检用 `sem(10)` 限流，10 条僵死连接即可占满信号量 → 主循环阻塞 → `wg.Wait()` 永不返回 → 配合 cron 的 `SkipIfStillRunning`，此后所有巡检被永久跳过且无任何告警。同样只在握手阶段设 deadline |
| 优化 | 前端主 CSS 减少 12% | `@ant-design/pro-components` 全量样式（829 个 `.ant-pro-*` 选择器）由静态 `@import` 打进主包且渲染阻塞——只访问登录页的用户也要下载整套 ProTable 样式。用它的 29 个页面全部是懒加载路由，故改为运行时异步 import，拆出独立 CSS chunk（主 CSS 619KB → 544KB，gzip 78KB → 69KB） |
| 优化 | 图表依赖树清理 | 改用 `@ant-design/plots` 按需引入，移除 `@ant-design/charts`（连带 G6/L7 整棵树），依赖包 1814 → 1603。**注：图表 chunk 体积未下降**——根因在 `@antv/g2plot` 缺 `sideEffects: false`，其 `esm/index.js` 的 re-export 使未使用的图表无法被 webpack 剔除；彻底解决需在 `config-overrides.js` 加 webpack 侧效应标记，属构建链改动且无法在本环境做运行时验证，**未实施**，详见下方「待决策」 |
| 修复 | 代码预览 10 万行 = 10 万 DOM 节点 | 行号列对每行渲染独立 `<div>` 且 `split('\n')` 未 memo。改为单个 `<pre>` + useMemo，并加 1MB 预览上限（超出提示下载） |
| 修复 | 26 处模块级共享 `React.createRef()` | 写在组件外导致所有实例共享同一 ref 对象。改为组件内 `useRef`（另修同类 1 处） |

| 场景 | 可用性 |

## v1.4.10 更新内容（性能与稳定性专项）

### 稳定性

| 类别 | 内容 | 说明 |
|------|------|------|
| 修复 | **MySQL 连接生命周期未设** | 连接池设了最大连接数，但未设最大存活/空闲时长。MySQL 服务端 `wait_timeout`（默认 8h）会单方面断开长连接，池中残留死连接在下次复用时抛 `invalid connection`，表现为**偶发接口报错、刷新即恢复**。现设 `ConnMaxLifetime(3h)` + `ConnMaxIdleTime(30m)`，主动回收早于服务端超时 |

### 性能

| 类别 | 内容 | 说明 |
|------|------|------|
| 优化 | **空闲 SSH 会话不再空转** | 原实现每个会话固定 60ms ticker，即使无数据也每秒被唤醒 16.7 次（100 个在线会话 ≈ 1670 次/秒无效唤醒）。现改为按需启停：有数据待刷新才启动 60ms 合并窗口，缓冲清空立即停表，**空闲时零定时唤醒**；"小包合并 + 大块立即刷"的交互语义保持不变 |
| 优化 | **RDP 鼠标/触摸移动节流** | 原实现每次 `mousemove` 都发一条 WebSocket 消息，快速拖动时每秒上百条，消息在「浏览器→Go→guacd→RDP」链路上排队，是操作跟手感变差的主因。现用 rAF 合并同帧内移动、只发最新位置（点击仍即时发送），并顺带减少 `showCursor` 调用 |

### 缺陷修复

| 类别 | 内容 | 说明 |
|------|------|------|
| 修复 | **RDP 画面缩放比例算错（两处）** | `Guacd.js` 两处缩放计算都写成 `高/远端高` 与 `宽/远端高`（第二项应为 `宽/远端宽`），比例取自 `min(窗口高, 窗口宽) / 远端高`。后果：窗口宽高比窄于远端画面时（如手机竖屏看 1920×1080 桌面）算出的比例偏大 ⇒ **画面右侧被裁切**，且因是位图拉伸而发虚。现按宽高两个方向分别取比再取较小者 |

## 快速开始

### Docker 部署（推荐）

```bash
# 1. 创建部署目录
mkdir -p /serverhub/next-terminal/data/sqlite /serverhub/next-terminal/guacd

# 2. 创建 docker-compose.yaml
cat > /serverhub/next-terminal/docker-compose.yaml << 'EOF'
services:
  guacd:
    container_name: guacd
    image: dushixiang/guacd:latest
    network_mode: host
    volumes:
      - /serverhub/next-terminal/guacd:/usr/local/next-terminal/data
    restart: always

  next-terminal:
    container_name: next-terminal
    image: next-terminal:v1.4.2
    network_mode: host
    environment:
      DB: sqlite
      SQLITE_FILE: /usr/local/next-terminal/data/sqlite/next-terminal.db
      GUACD_HOSTNAME: 127.0.0.1
      GUACD_PORT: 4822
      SSHD_ENABLE: "true"
      SSHD_ADDR: 0.0.0.0:8089
    volumes:
      - /etc/localtime:/etc/localtime
      - /serverhub/next-terminal/data:/usr/local/next-terminal/data
    restart: always
EOF

# 3. 启动
cd /serverhub/next-terminal
docker-compose up -d
```

访问 `http://<服务器IP>:8088`，默认账号 `admin` / `admin`。
